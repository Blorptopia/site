Streaming

Instead of taking all the input in all at once initially, we can take in rows a bit a time and return the serialized result as we process it. This will reduce the latency from submitting a part of the input to it being sent back to the end user, however it does not improve bandwidth To do this we take in an AsyncIterator of rows and return an AsyncIterator of text chunks. The user of the text chunk iterator then only has to concatenate the chunks together to get the final CSV.

Multi threading

As we are sometimes serializing large amounts of rows, we want to optimize our serializer at least a little bit so we don't have to wait that long. As we already converted our interface to use AsyncIterators when we added streaming we can keep the interface the same so we can easily swap between the two for example when benchmarking. As the serializer doesn't require state to serialize rows, this is quite a good candidate for multi threading. Multi threading then just becomes a matter of chunking up a group of rows and sending it to a worker pool and joining them by newline when they come back. We do this with a custom pull-based worker pool instead of a normal push-based worker pool as it allows the user to feed us whatever sized chunks and as long as our buffer is large enough when a worker is available, we send the optimal task size to the worker. The pull based worker pool is also built around a poll function, not a AsyncIterator.

While yes you should generally follow standards, the reason I decided to deviate was that an AsyncIterator holds a value pending at all times, instead of poll where the value is only generated when requested. This is one of the things allowing us to change the prioritization of tasks right up until we sent it to the worker.

Since this is targeting both browser and node, we use the web-worker wrapper around web workers and node's worker_threads.

Deserializing

De-serialization is the part where you turn the CSV file into native objects (in this case an array of Maps). The de-serialization process is split into two stages:

  1. Parsing the header row
  2. Parsing the data rows

In header row mode we allow any count of columns and just eat the row into an internal "columns" array. Once that is done we proceed into the data row stage, where we lookup the index of the column in the columns array to get the name.

The control characters strike again

To parse CSVs with control characters we use an state machine with two states:

  1. Normal
  2. Escaped

Normal mode is the initial mode, while escaped mode is the mode you enter when you enter a quoted column.

Escaped mode switches the behavior of a few control characters, like making comma just emit a comma instead of ending the column, and two double quotes after each other emitting a single double quote instead of toggling escaped mode on and off. Note that escaped mode can only be entered and exited at the start and end of columns, not in the middle.

Multi threading

To multi thread the parsing of the rows, we need to split the work up into smaller tasks that we can distribute through a worker pool. We do this through seeking forward an "ideal" chunk size and going character by character until we hit a newline.

This works perfectly in the case where the input doesn't contain any newlines inside columns, however in the case that it does this method might end up splitting a column in the middle of it. This is hard to avoid considering there can be a full CSV inside of one column of CSV without issue. We solve this later when parsing by allowing tasks to exceed their target boundaries if they are in escaped mode when reaching the end of their target boundary up until the row actually ends. This requires that we cancel the task after it and re-schedule it with a new start size.

Note the tradeoff of this is that we can't just send the slice of buffer that the task is supposed to be parsing, but also everything after. Benchmarking if this is more efficient will be another project for another day.

Here we also use the custom pull-based worker pool described when we made the multi threading serializing however it provides major speedups in reducing head of line blocking due to it allowing us to specify the order of tasks executed instead of queueing it like a FIFO queue and even changing the priority up to right before a task gets sent to a worker. This is especially important when we have to resize a task as that would normally be submitted at the back of the queue even though the chunk is at the start of the text, making the entire output wait until that chunk is complete. However when we can prioritize we can put tasks that are closer to the start first, reducing head of line blocking as much as possible.
